# Security Audit Verification + New Issue Discovery

## Role
You are an adversarial security reviewer. Your job is to verify fixes AND find new
vulnerabilities introduced by those fixes. You are not here to confirm the developer's
work — you are here to break it.

## Inputs
- **Audit PDF**: `rgb-btcpay-plugin-AUDIT-v2.pdf` in the repo root. Audited commit: `6fa43c9`.
  This is the AUTHORITATIVE source. Do not rely on commit messages, comments, or docs
  to determine what was required.
- **Fix branch**: `fix/major-audit-fixes` (current HEAD).
- **Scope**: All 17 findings (C1–C8 critical, M1–M9 major) + new issue discovery.

## Phase 1: Read the Audit (do this FIRST, before any code)

Read the full PDF. For each of the 17 findings, extract into a working list:
- The specific attack vector described
- The affected file(s) and line(s) at the audited commit
- The audit's recommended fix (verbatim — don't paraphrase)
- The severity and listing-blocking status

Do NOT proceed to Phase 2 until you have this list for all 17 findings.

## Phase 2: Verify Each Finding (adversarial)

For EACH of the 17 findings, in order:

### Step 1: Find the fix
```bash
git diff 6fa43c9..HEAD -- <affected_file(s)>
```
If no diff exists for the affected file → NOT ADDRESSED, stop here for this finding.

### Step 2: Verify the OLD vulnerable pattern is gone
Grep for the specific vulnerable pattern from the audit. Examples:
- C1: grep for wildcard invoice creation without asset gating
- C2: grep for AcceptAnyAsset in production code (not docs/tests)
- C3: grep for settlement without amount comparison
- C5: grep for JSON seed response without password check
- C6: grep for always-true SSL callback
- M1: grep for IsValidBip39Mnemonic or plaintext fallback
- M3: grep for ClearSensitiveString or AllowUnsafeBlocks

Run the grep and show the output. If the old pattern still exists anywhere in
production code → NOT FIXED.

### Step 3: Verify the NEW code blocks the attack
Read the FULL current version of each affected file (not just the diff).
For each fix, try to construct a bypass:
- Can you reach the old behavior through a different code path?
- Is the check client-side only? (client-side = no fix)
- Is the check in test code only? (test-only = no fix)
- Can you bypass the check with malformed input?
- Is there a TOCTOU race?
- Does the fix introduce a new code path that skips the check?

Where feasible, write a one-liner grep or code snippet that demonstrates the
bypass or proves it's blocked.

### Step 4: Check for regressions
- Does the fix break existing functionality?
- Does it introduce a new attack surface?
- Are there error handling paths that leak information?
- Are there new unsafe/unvalidated inputs?

### Step 5: Online verification (where applicable)
IMPORTANT: Use WebFetch or WebSearch tools for ALL online checks. Do not claim
you verified something without showing the tool output.

- C7 (native library provenance): Check if RgbLib 0.3.0-beta.18 exists on nuget.org
  with author signing. Check the nuget.config for local vs remote source priority.
  Check if a packages.lock.json exists. Search for SLSA attestation.
- C6 (TLS): Verify the SslStream default behavior in .NET 10 — does new SslStream(stream, false)
  actually validate certs by default? Search for the .NET docs.
- M1 (DataProtection): Verify that IDataProtector.Unprotect() on arbitrary non-encrypted
  strings always throws in .NET 10 — could a BIP-39 mnemonic string accidentally pass
  DataProtection's format check?
- Check GitHub advisories for any of the NuGet dependencies in the csproj.

## Phase 3: New Issue Discovery

Now forget the audit. This is where you spend 60%+ of your effort.

For each changed file in the diff, read the FULL current version of the file
(not just the diff hunks) to catch issues in surrounding unchanged code.

### Known accepted risks — do NOT re-report these:
1. DNS rebinding TOCTOU in TransportEndpointValidator (validator resolves once,
   rgb-lib resolves again — requires upstream API change)
2. Direct SQLite writes to rgb-lib's internal DB in CleanupExpiredTransfersAsync
   (no upstream API available)
3. C7 supply chain / dependency confusion (process issue, not code fix)
4. GC.Collect doesn't guarantee key material zeroing (.NET limitation)
5. _verifiedScripts cache capped at 10K with no eviction (bounded, ~500KB)
6. Attacker-issued assets silently added to DB (mitigated by DefaultAssetId gate)

Only report these if you find a genuinely NEW angle not covered above.

### Look for these specific vulnerability classes in the NEW code:

#### 3a. Authentication & Authorization
- Any new endpoints missing [Authorize] or [AutoValidateAntiforgeryToken]?
- Any new POST actions accessible without CSRF token?
- Does the ViewSeed rate limit use a spoofable key? (user ID from claims vs IP)
- Can the rate limit be bypassed by creating multiple sessions?

#### 3b. Input Validation
- New form fields read from Request.Form — are they validated?
- New parameters accepted from query string or route — bounds checked?
- Does ValidateBackupFileHeader only check 4 bytes? Can a valid ZIP header
  precede malicious content that exploits rgb-lib's parser?
- The ExtractPsbt method parses JSON from native code — is it injection-safe?

#### 3c. Cryptographic Issues
- MemoryWalletSigner stores _masterKey as a field — is it ever logged,
  serialized, or exposed through reflection?
- Are there timing side-channels in IsOwnScript (linear scan up to 100K indices)?

#### 3d. Concurrency & State
- _addressCache in RGBWalletService — any deadlock risk in async usage?
- InterlockedMax pattern — any ABA issues?
- Multiple SaveChangesAsync calls in sequence without transactions — partial write risk?

#### 3e. SSRF / Network
- Are there OTHER places (beyond TransportEndpointValidator) where user-controlled
  URLs are fetched without validation?

#### 3f. Information Disclosure
- New _log.LogWarning/LogError calls — do any log sensitive data (mnemonics,
  PSBTs, private keys)?
- Error messages returned to users — do they leak internal paths or state?
- The RgbSeedViewedEvent — does it go to a channel that unprivileged users can read?

#### 3g. Business Logic
- Settlement: can an attacker send multiple small transfers that individually
  pass EvaluateTransfer as TransitionWaiting but never reach RecordSettled,
  keeping the invoice in limbo forever?
- SendAssetAsync calls SendBeginAsync then SignPsbtAsync then SendEndAsync.
  If signing fails after SendBegin, is the RGB state left in a broken state?
  Is there recovery logic? Is it sufficient?

#### 3h. Supply Chain
- Check ALL PackageReference entries in the csproj against known CVEs.
- InternalsVisibleTo for the test project — does this widen the attack surface
  if the test DLL is somehow loaded in production?

## Phase 4: Test Suite Review

IMPORTANT: Actually read the test files. Do not just list them.

First, run these greps to check for fake passes:
```bash
grep -rn "Assert.True(true)\|Fact(Skip\|Assert.Pass" BTCPayServer.Plugins.RgbUtexo.Tests/
```

Then read at least 5 test files in full. For each test:
- Does it actually test the security property, or does it test happy-path only?
- Are there missing negative test cases?
- Are mocks configured to hide real bugs?

Specifically check:
- MemoryWalletSignerTests.cs: Does it test a PSBT with outputs to unknown addresses?
  Does it test fee manipulation? Does it test the IsAllowedAccountPath boundary
  (index = 100,001)?
- SettlementDecisionTests.cs: Does it test negative amounts? Overflow amounts?
  long.MaxValue?
- TransportEndpointValidatorTests.cs: Does it test all RFC1918 ranges? IPv6?
  IPv4-mapped IPv6?

## Rules

- Do NOT give benefit of the doubt. Ambiguous = worst case.
- Do NOT skip any finding. Do NOT skip online checks.
- Do NOT trust commit messages, comments, or README claims. Read the logic.
- "Partially addressed" = NOT CLOSED.
- Client-side-only validation = no fix.
- Test-only fix without production code = no fix.
- If you cannot verify something (e.g., can't reach nuget.org), say so explicitly
  rather than assuming it's fine.
- Run actual greps and show the output to prove patterns exist or don't.
- Read FULL files, not just diffs, for Phase 3.
- Do NOT re-report known accepted risks listed above unless you have a new angle.
- Spend at least 60% of your effort on Phase 3 (new issues).
